## 六维评审

### 一、代码思路（Technical Correctness）— 7/10

#### ✅ 好的

- **Bug-1 修复方案正确**：预先扫描所有文件确定 `maxColumnsOverall`，`SOURCE_COL_IDX` 全局固定，不再漂移
- **去重逻辑正确**：不再假设来源列在末尾，使用 `sourceIdx` 精确定位排除
- **`fillNewColumnStyles` 有判空保护**：`worksheet[sourceAddr] && worksheet[sourceAddr].s` 避免了无样式列崩溃
- **Time-Slicing 参数可配置**：`CHUNK_SIZE`（500）和 `YIELD_MS`（16）可调

#### ❌ 仍有问题

**1. 模式一的代码样例与架构矛盾（最严重）**

L186-244 的 `split-sheet` 代码仍使用：
```javascript
self.onmessage = function(e) { ... }   // Worker 入口
self.postMessage(...)                   // Worker 通信
await zip.generateAsync(...)           // 带 transferables
```

但 1.3 节架构已改为"不引入 Web Worker，用 Time-Slicing"。两处矛盾。**实现者看到会困惑：到底按哪个写？**

**2. `fillNewColumnStyles` 的 JSON.parse(JSON.stringify) 风险**

L562：
```javascript
worksheet[targetAddr].s = JSON.parse(JSON.stringify(worksheet[sourceAddr].s));
```

- `JSON.parse(JSON.stringify(obj))` 丢失 `undefined`、`Date`、`RegExp`——前面报告已确认为 Perf-23
- 如果 `worksheet[sourceAddr]` 是数字单元格（`t: 'n'`），硬赋值为 `{ t: 's', v: '' }`，SheetJS 写出时行为不可预测
- 安全做法：`Object.assign({}, worksheet[sourceAddr].s)` 或 `structuredClone()`

**3. `processWithYielding` 的 CHUNK_SIZE 固定 500 可能太长**

L57-59 每 500 个 item 才 yield 一次。如果单次 `processFn` 耗时 100ms（如单元格级复杂操作），500 个 = 50 秒阻塞，等于没切片。

建议：CHUNK_SIZE 应作为可调参数，或根据单次 `processFn` 耗时动态计算。

### 二、业务思路（Business Value）— 8/10

#### ✅ 好的

- **定位清晰**：坚持"离线轻量工具"，没有去和方方格子/Kutools/WPS 正面竞争
- **功能选择有依据**：按行数拆分（Kutools 有）、按名称归类合并（方方格子有）——来自竞品调研
- **砍掉 Worker 是正确决策**：节约了大量开发时间，聚焦在真正的用户价值上
- **工期可控**：3-3.5 天说明清楚"什么该做，什么不该做"

#### ❌ 缺失的

**1. 没有用户数据支撑优先级排序**

五个功能的排期依据是什么？按行数拆分放在 Day1，智能合并放在 Day2。但如果真实用户更常做合并操作，这个顺序就反了。文档没有来自实际用户或 issue 的数据支撑排期决策。

**2. 没有"发布后反馈收集"机制**

3.5 天开发完后，怎么知道做对了？文档没有提上线后的数据收集或用户反馈计划。

**3. 旧模式删除没有迁移方案**

删除 `merge-file` 和 `merge-sheet` 替换为"智能合并大师"。现有用户如果习惯了旧 UI，会找不到功能。文档没有说怎么处理这个过渡。

### 三、使用者思路（User Experience）— 7/10

#### ✅ 好的

- **4 步向导保持**：用户已习惯的交互流程不变
- **模式选择面板清晰**：5 个模式 2 行布局，一目了然
- **智能合并大师的 UI 改进**：自动按名称归类分组展示，比现有体验好
- **单元格预警**：主动防卡设计，好过卡死后报错
- **自定义命名规则**：给高级用户灵活性

#### ❌ 用户视角的问题

**1. "处理模式"开关位置可能让用户困惑**

3.1 节 UI 图显示"处理模式"在 Step 1 全局配置。但每个模式在 Step 3 也有自己的"处理模式"配置。用户会困惑：
- 哪个生效？全局还是模式级？
- 如果一个选"保留格式"、一个选"仅数据"，冲突怎么处理？

建议：要么只有全局开关，要么只有模式级开关，不要两层都有。

**2. "单文件多Sheet"在 split-rows 模式下体验差**

用户把大表切成 100 份，选"单文件多Sheet" → 得到 1 个 xlsx 里 100 个 Sheet → 要在标签页里从 P01 翻到 P100。文档没有解释为什么提供这个选项，也没有限制合理上限。

**3. 删除旧合并模式没有用户过渡期**

升级后 `merge-file` 和 `merge-sheet` 突然消失。至少应该有工具提示或弹窗说明"已迁移到智能合并大师"。

### 四、产品经理思路（Product Strategy）— 7/10

#### ✅ 好的

- **竞品差异化明确**：竖向拆分（独家）、零安装（vs Office/WPS）、隐私（不上传）
- **功能取舍合理**：没有引入 TypeScript、构建工具、CLI 等偏离定位的功能
- **增量交付**：Day0 修 bug → Day1-2 核心功能 → Day3-4 体验优化

#### ❌ 产品层面的问题

**1. "按行数拆分"的需求来源不足**

竞品调研显示 Kutools 有、方方格子没有、WPS 没有。但这不能证明用户需要。有没有收到过用户反馈要求这个功能？还是因为竞品有所以加？如果答案是后者，应该先验证需求。

**2. 模式B（按名称归类）缺少 Sheet 名归一化策略**

Map 分组时：
- "销售数据"和"销售数据 "（尾部空格）→ 两个组
- "Sheet1"和"sheet1"（大小写）→ 两个组
- "南京 2024"和"南京　2024"（全角空格）→ 两个组

文档没有说怎么处理这些边界情况。

**3. 去重只在合并模式有，拆分模式没有**

用户可能在拆分前想去重。比如按列拆分时先去掉重复行。文档只把去重放在 merge 里，但 split 场景也有这个需求。

**4. 没有定义 MVP 的可砍边界**

Day0-Day4 = 3-3.5 天。如果做到 Day3 发现时间不够，什么可以砍？文档没有定义"必须交付"和"可以延后"的边界。

### 五、开发思路（Engineering Feasibility）— 7/10

#### ✅ 好的

- **增量修改为主**：没有破坏性重构，在现有代码上做加法
- **Time-Slicing 侵入性低**：通过 `processWithYielding` 通用函数实现，调用方只需改循环结构
- **任务粒度适中**：每个任务半天到一天，可独立测试
- **自测兼容性在考虑范围内**：T4.4 专门验证 async 兼容性

#### ❌ 开发视角的问题

**1. T0.2 估 0.25-0.5d 修 12 个 P1 bug（最重要的问题）**

12 个 bug 包括：
- `cloneWorksheet` 降级路径逻辑修改（Defect-16）——涉及对 SheetJS 内部结构的理解
- `resetTool` 的 DOM 操作重构（Bug-5）——涉及多处调用点的回归测试
- `beforeunload` 状态管理改动（Defect-12）——需要理解用户操作流程

每个 bug 平均 10-20 分钟。对于有自测系统的项目，改完还要跑 T01-T122 验证。**建议至少估 0.5-1 天。**

**2. T1.1 和 T1.2 挤在同一个 0.5 天**

0.5 天里同时做"给所有大循环加 Time-Slicing"和"新增一个完整新模式"。要在 6757 行代码中找到所有大循环位置加切片，同时新增一整套 HTML + 事件 + 业务逻辑。更合理：T1.1 先做，T1.2 顺延或用更多时间。

**3. 没有定义"改完怎么验证正确"的机制**

除自测外，没有每个任务的验收标准。比如 T2.2 "模式A：全量纵向追加"完成的标准是什么？3 个测试通过？不崩溃？用户手动验收？

### 六、实施思路（Project Management）— 7/10

#### ✅ 好的

- **Day0 先修 bug 再开发**：基线干净后再加新功能，正确的顺序
- **任务粒度适合单人维护**：每个任务 0.1-0.5 天，可独立完成
- **总工期 3-3.5 天**：容易承诺和跟踪
- **Day4 预留回测时间**：不是开发完就结束

#### ❌ 实施层面的问题

**1. 任务依赖关系未定义**

- T1.2（按行数拆分）依赖于 T1.1（Time-Slicing）吗？还是可以并行？
- T2.x（智能合并）必须等 Day0 bug 修完吗？新的 `mergeAppend` 不直接调用旧的 `performSheetDataMerge`，但从逻辑上应该先修 Bug-1 再写合并代码

**2. 无风险清单**

3.5 天计划可能遇到的问题：
- `XLSX.read()` 解析 50MB 文件卡 UI 3-5 秒——已承认但未提缓解方案
- JSZip `generateAsync` 内部进度回调是同步的，Time-Slicing 插不进去
- 自测框架改造比预期复杂（Day0 修了 19 个 bug 可能导致 T01-T122 行为变化）
- 开发者对 6757 行代码的熟悉程度影响效率

**3. 没有回退机制**

文档说"全部确认后立即实施"。但如果 AI 生成的代码不符合预期，怎么回退？git 回滚是一个方案，但文档应该提到。
