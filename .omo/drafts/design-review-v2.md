# DESIGN.md v2.0 设计评审

> 基于对 DESIGN.md v2.0 的逐项审查，2026-06-03

## ✅ 强烈支持的决策

| 决策 | 理由 |
|------|------|
| **Vanilla JS + 无构建工具** | 保持"双击即用"的核心竞争力 |
| **按行数拆分（新模式）** | 高频需求，竞品已验证 |
| **智能合并大师模式B（按名称归类）** | 竞品调研确认的 P0 级缺失功能 |
| **自定义命名规则** | 强用户体验提升 |
| **处理模式开关（保留格式/仅数据）** | 对大数据量用户是救命功能 |
| **合并去重** | 实用性强，实现简单 |
| **单元格数预警** | 纯前端抗大文件的必要保护 |

## ⚠️ 三处风险

### 1. 🔴 Worker 架构是"赌注式"重构

将 6757 行单线程 JS 重构成 `Worker工厂 + 6个Worker业务 + 主线程通信协议`，是全量重写。

**问题**：
- CSP 兼容风险：`script-src 'self' 'unsafe-inline'` 需加 `blob:`，或移除 `'unsafe-inline'`
- FakeWorker 降级不完整：只发了 warning，未执行 Worker 中的业务逻辑
- Worker 内异常无法被 `window.onerror`（L1321-1336）捕获

**建议**：Worker 方案标注为"探索性"，先实现功能升级（Phase 1），Worker 作为独立 Phase X

### 2. 🟡 SheetJS + JSZip 内嵌使 HTML 膨胀至 ~750KB+

当前 `<script src="lib/xlsx.full.min.js">` 可被浏览器缓存。改成内嵌后：
- HTML 从 ~250KB → ~750KB+
- 每次修改 HTML 需重下整个文件
- 编辑体验变差

**建议**：保持外部 `<script src>` 加载

### 3. 🟡 12-16 天工期过于乐观

| Phase | 设计估算 | 现实估算 | 原因 |
|-------|---------|---------|------|
| P0 Worker架构 | 2d | 5-7d | CSP、FakeWorker、错误传播等边界 |
| P1 核心功能 | 5-7d | 7-10d | 合并模式B + 去重 + 按行拆分 |
| P2 输出体验 | 3-4d | 3-5d | 命名规则 + 多格式输出 |
| P3 收尾 | 2-3d | 3-5d | Playwright 40+ 测试、跨浏览器 |
| **合计** | **12-16d** | **18-27d** | |

## 🐛 设计遗漏

### 4. Bug-1（来源列漂移）在 smart-merge 设计中重现

DESIGN.md `2.6 模式A` 中 `sourceColumnIndex` 仍然在每次迭代中变化（3→5→7...），且 `migrateSourceColumn` 函数声明但未定义。

**建议**：来源列位置应**全局固定**为所有文件中最大列数+1

### 5. 竖向拆分"ZIP/单文件"的输出自相矛盾

2.4 节说"此模式强制 ZIP 输出"，但配置表中又加了 "ZIP / 单文件多Sheet" 选项。

**建议**：保持强制 ZIP，删除矛盾选项

## 🎯 建议实施顺序

```
Phase 0（当前）：先修复已确认的 19 个 bug → 已有计划 .omo/plans/fix-confirmed-bugs.md
       ↓
Phase 1（功能新增）：按行数拆分 + 智能合并大师（模式B）+ 自定义命名规则 + 去重
       ↓
Phase 2（体验提升）：处理模式开关 + 单元格预警 + 单文件多Sheet输出 + 保留底部行
       ↓
Phase X（探索）：Worker 架构 —— 仅在前三阶段稳定后投入
```

**理由**：19 个已知 bug（含数据级错误）优先级应高于 Worker 架构变更。增量升级比全量重写更可控。
